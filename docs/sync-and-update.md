# 同步与更新检查规范

更新日期：2026-10-11。

本文集中定义桌游资料检查、WebDAV 可用性检测、账号数据同步和应用版本检查。术语与职责以本文为入口，协议及平台细节由链接的专项文档维护。

本文同时列出已确定的规范和当前源码的实现状态。文档更新不等于调度、自动更新或界面已经改动；不得把未实现的行为写成现有功能。

## 1. 职责划分

| 名称 | 检查或处理什么 | 不代表什么 |
| --- | --- | --- |
| 桌游资料快速检查 | 轻量读取远端目录，验证可读取并比较目录变化 | 不保证发现目录不变时的 PDF、图片内容修改 |
| 桌游资料完整检查 | 比较目录，并检查已登记资源的服务器版本信息，汇总差异 | 不下载所有正文计算 SHA-256，也不遍历 NAS 上所有未登记文件 |
| WebDAV 可用性检测 | 当前入口、凭据及知识库目录是否能真实访问 | 可用不等于所有资料已经检查或更新到最新 |
| 账号数据同步 | 同账号私人数据恢复，以及公开收藏、投票记录的发布和汇总 | 不检查或下载桌游规则资料，也不更新 APK/EXE |
| 应用版本检查 | 当前平台是否有新的安装包版本 | 不等同于桌游目录或规则更新 |
| 登录会话验证 | 群晖身份与会话是否仍然有效 | 不等同于资料更新检查或业务数据已同步 |

## 2. 本次确定的资料检查原则

- 初始化启动尝试一次完整检查；周期性任务采用轻量快速检查，避免周期性重复探测全部资料。
- 保留现有 `catalog.json`、各游戏 `game.json` 与 `manifest.json`，继续利用服务器返回的文件版本信息。本轮不要求新增统一 SHA-256 版本清单，也不把给 manifest 增加摘要作为前置条件。
- 周期基准沿用现有的 **60 秒**。快速检查和可用性检测应复用同一次目录读取结果；该复用目前尚未完整实现，状态见下一节。
- 手动重新检查采用完整检查。本文不引入此前讨论过的每 600 秒完整扫描规则，也不承诺目前每次进入游戏库都会请求更新。
- NAS 管理及资料维护负责正确提供文件内容、权限和 ETag/Last-Modified/大小等响应信息；项目上传端负责资源登记、路径和上传结果正确。客户端按该信息比较，不要求日常读出全部 PDF 重算摘要。
- 检查、下载和账号同步分别报告结果。检查完成且存在变化，仅表示有待更新项；只有下载、校验和本机落地完成，才表示资料已更新。

## 3. 当前源码的实际触发与频率

| 任务 | 当前实际触发与频率 | 实现状态 |
| --- | --- | --- |
| 资料完整检查 | 初始化时尝试一次；资料更新页手动“重新检查”；打开历史通知但内存中没有待更新清单时重新检查 | 已实现，没有固定周期的全库检查定时器 |
| WebDAV 可用性检测 | 初始化链路中一次，之后每 **60 秒**，另有手动刷新入口 | 已实现；目前验证目录可读取，没有把取得的目录用于更新差异比较 |
| 周期资料快速检查 | 规范要求与上述 **60 秒**目录请求合并 | 目录差异比较及变更处理尚未接入周期任务，不得声称已经每分钟发现资料变化 |
| 账号数据同步 | 登录后、保存收藏/投票后、手动同步、进入/刷新排行榜，以及每 **60 秒**补拉 | 已实现，具体规则见第 7 节 |
| 其他私人数据编辑 | 修改稳定约 **4 秒**后触发私人同步 | 已实现，与收藏/投票的立即同步区分 |
| 登录会话验证 | 初始化恢复、返回前台及登录状态下每 **60 秒**验证 | 已实现，复用账号服务自己的会话检查 |
| 应用版本检查 | 自动检查开启时，启动后一次；另有手动检查入口 | Windows/Android 已实现，没有按分钟或小时重复运行的版本检查定时器；Web 不安装 APK/EXE |

上述周期由应用内 Dart Timer 调度。它不是系统后台任务，移动端后台和进程终止后的执行受系统限制，不保证每个周期都在后台准时发生。

初始化资料链路当前按顺序执行：资料索引刷新 → 图片预缓存 → 可用性检测 → 完整更新检查。冷缓存时，前置资源请求也会影响检查开始时间。资料检查需要登录及资源访问条件成立；被跳过、失败或中断都不能算一次成功的完整检查。

## 4. 目录、资料登记和文件版本

| 数据 | 职责 |
| --- | --- |
| `assets/catalog.json` | 注册桌游，控制排序、启用及分类；远端为 overlay，缺少条目不自动删除内置桌游 |
| `assets/games/<slug>/game.json` | 游戏信息、展示文案、图片路径及配置 |
| `assets/games/<slug>/manifest.json` | 登记资料路径、类型、来源、状态、用途和 AI 许可 |
| 客户端版本记录 | 原生 `_asset_versions.json`；Web 偏好键 `library.assetVersions.v1`，记录已观察或下载文件的服务器版本信息 |

当前 catalog/资源 manifest 没有承担全库内容 SHA-256 清单的职责。它们的结构版本或桌游版次不是“每次改 PDF 自动增加”的总更新计数器。

目录比较读取远端 JSON，再读取本机缓存目录；没有缓存时使用内置目录。JSON 规范化后比较完整内容，忽略空白与对象字段顺序，数组顺序仍参与比较。新增桌游、启用状态、排序或分类改变，即使 `version` 数字不变也会被识别。

同路径 PDF 或图片被替换时，目录和资源登记可以不变。完整检查对此文件发送 HEAD，将返回的 ETag、Last-Modified、Content-Length 与客户端历史记录比较。ETag 是服务器提供的版本标识，不要求它等于 MD5 或 SHA-256。没有历史记录时建立基线，不能据此宣称已经验证过旧文件正文。

服务器版本信息改变时，现有完整检查可发现同路径资源修改。若服务器在内容变化后仍返回相同版本信息，当前元数据比较不能识别；客户端也不把一次目录读取宣传为文件正文完整性审计。

## 5. 完整检查与更新执行

当前完整检查：

1. 获取目录，比较并整理新增、排序、分类、停用等变化。
2. 新游戏读取 `game.json` 与资源 manifest，整理其资源路径。
3. 继续检查现有游戏已登记的图片、文档、配置和资源 manifest；排除 `docs/others`。检查范围不等同于遍历 NAS 全盘。
4. **每批最多 4 项异步网络探测**；整批完成后才开始下一批。没有新建 4 个扫描线程或 Dart isolate。单文件还可同时尝试多个配置入口，因此在途 HTTP 请求数可能多于 4。
5. 配置或资源 manifest 变化时，再获取 JSON 整理字段及资源登记差异；最后生成待更新清单与通知。

当前每个资源请求默认 **8 秒**超时，探测阶段设 **2 分钟**检查预算，在批次边界检查预算，并非覆盖所有前置/后置工作的硬性总截止时间。探测失败不能作为已核实无变化的证据；现有 `hasRemoteChanged` 在无法获取版本时返回 false，这个实现限制应在诊断时保留，不能宣称完整检查是逐字节验证。

当前更新仍需用户在共用资料更新界面确认。下载顺序为资源文件 → JSON 配置 → catalog，更新预算 **15 分钟**，在请求之间检查；验证资源非空、JSON 结构及真实远端下载结果，原生缓存先写临时文件再替换。失败保留待更新清单和重试入口，不进行整批事务回滚，也不删除用户文件。

此前讨论的“进库快查、直接自动更新、桌面横向进度栏、App 旧版数量进度、跨页任务提示”尚未因本文落地。当前行为及验证见 [资料更新通知与确认](library-update-review.md)。

消息中的“有 N 项资料等待更新”来自最近一次产生该通知的检查，是已保存的通知信息，不是每分钟实时统计。通知时间也不等于最新一次服务器检查时间；历史通知缺少当前待更新清单时，需要重新检查。

## 6. 资料上传端的责任

- 正确登记 catalog、游戏配置与资源 manifest，确保路径、启用状态、资料用途和实际上传文件一致；继续排除 `docs/others` 运行资料。
- 先上传正文及图片，再提交依赖它们的配置和目录，验证上传后的文件内容、大小及可读取性。传输校验可使用 SHA-256，但它不要求成为 catalog 的新增字段。
- 不将失败或未传完的文件宣布为发布成功；不以客户端缓存命中代替远端上传验证。
- Android APK 不内置桌游正文，运行时通过已登录账号按需下载缓存；完整检查不代表必须预下载全部正文。
- 不部署新的 NAS 服务来计算或维护清单，不擅自修改 NAS 权限，不以开发诊断为由清理真实账号资料。

## 7. 账号数据同步

账号同步与资料检查使用不同业务协议，不能用一个“WebDAV 可用”状态代表账号数据已经同步。

私人数据包括收藏、想玩、专题清单、历史、每日推荐、AI 对话、昵称和个人偏好。公共数据只包含收藏/投票必要的账号记录与版本，用于人数及排行榜；凭据、API Key、通知、资料缓存和应用更新状态不公开同步。

- 先成功保存本机业务数据，再持久化版本操作及待同步记录。收藏/投票立即启动公共发布，并触发需要的私人增量传输，**不等待 4 秒或 60 秒定时器**。
- 其他私人编辑采用 **4 秒**防抖；登录初始化和每 **60 秒**补拉覆盖恢复与重试。进入/刷新排行榜请求公共统计，不等待整个私人 AI 对话同步完成。
- UI 只有一个同步入口；内部公共与私人网络任务独立，本机日志写入串行。私人合并需要本机数据稳定，公共投影只处理收藏/投票，不打断活动中的 AI 对话。
- 私人链路直接复用 `webdav_sync` 的 `IncrementalSyncEngine`、不可变操作、去重、游标和恢复；通过 `app_identity` 的 FileStation 适配访问当前账号 home。
- 公共链路按 UID 发布当前设备快照，写后读回核对，重新读取各账号记录并汇总。每个 UID 对一款游戏最多贡献一次，取消保留版本标记，不覆盖一个公共总数来盲写 `+1`。
- 公共失败最多自动补试两次，等待 **3 秒、10 秒**；私人引擎每个请求最多两次尝试，后续由手动或定时任务继续。私人引擎每轮最多 8 轮、批次 100 条，设 120 秒超时；公共任务每轮设 20 秒超时。
- 账号总开关同时暂停公共和私人云端读写；本机编辑保留，恢复后补交。切换账号或取消后的迟到请求不得覆盖新账号状态。
- 私人失败不让已确认的排行显示失败；公共上传已确认但统计刷新失败与仅本机保存，分别说明实际完成情况。

私人新日志：`/home/Apps/board_game_agent/sync/v1/<environment>/operations/d<device>.<sequence>.json`。旧设备子目录只兼容读取，不搬迁或删除。公共快照：`/<共享目录>/apps/board_game_agent/public/v1/u<UID>/d<device>.json`。公共根由管理员准备；App 只受控初始化当前账号自己的固定目录，上传不隐式创建任意父目录。

详见 [账号云同步](account-cloud-sync.md)、[公共账号数据](public-account-data.md) 和 [喜欢排行榜](favorite-rankings.md)。

## 8. 共享包的边界

| 功能 | 复用范围 |
| --- | --- |
| 资料快速/完整检查 | 应用自己的目录比较、HTTP GET/HEAD、调度与差异逻辑；目录列举复用 `webdav_storage`，JSON 规范化借用 `webdav_sync`，不调用其增量同步引擎 |
| 桌游私人账号同步 | 调用共享 `webdav_sync.IncrementalSyncEngine`，应用负责业务存储和 FileStation 适配 |
| 公共收藏/投票 | 应用负责 UID 快照与汇总，复用共享操作格式和版本规则 |
| Zheri 业务数据同步 | 同一个共享增量引擎，业务适配为 SQLite changeset，远端采用 `WebDavSyncStore`；与桌游资料检查不相同 |
| APK/EXE 更新 | 复用 `app_about`、`remote_update`、`remote_update_webdav` 的清单读取、版本判断、下载校验及安装适配 |

应用安装包的更新清单与游戏资源 manifest 是不同文件，不能混用。应用检查只读取当前平台的安装包清单；下载安装包仍需确认，失败保留可续传部分，完整包校验后才安装。正在检查、下载或安装应用更新时，资料通知不弹出打断，待更新状态保留。详见 [Windows 应用内更新](windows-updates.md)。

## 9. 维护与验收

修改检查或同步时，同步更新本文的“规范”和“当前实际状态”，明确触发点、秒数、并发、失败、重试与平台边界。没有完成的调度或界面不得只通过修改文案标为已实现。

验收应确认：初始化完整检查、周期轻量请求不触发全库扫描、同一请求可用性/差异结果的复用、手动完整检查、任务合并、登录及来源切换丢弃旧结果、通知时间与实时状态区分、跨页进度、失败保留本机数据，以及私人失败不污染公共排行。
